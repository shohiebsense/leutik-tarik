## Verdict

The slice-1 shape is right (OTLP → normalized span → server-rendered
operations/detail, no JS, Go only). It is **not** a foundation I should build
ClickHouse on top of yet: the data model is too thin, the schema's sort key is
wrong for the product's primary query, ingest cannot accept a real exporter's
traffic, and three documents state things that are false. All of that is cheap
to fix now and expensive after storage exists.

Findings: **30**, of which **6 blocking**, **9 must-fix-before-ClickHouse**,
**15 fix-in-phase**.

## Blocking (fix before anything else ships)

### B1. Ingest rejects a stock OTel exporter — no protobuf

OTLP/HTTP's default content type is `application/x-protobuf`. The receiver
decodes JSON only, so a default-configured OTel SDK gets a 400. This is the
single biggest hole: the platform currently cannot ingest real traffic from any
standard instrumentation, which undermines the whole "automatic first"
premise. Fix: accept both, JSON via `encoding/json`, protobuf via
`go.opentelemetry.io/proto/otlp` + `google.golang.org/protobuf`. OTel's own
`pdata`/`ptrace` packages are the mature route over hand-rolling.

### B2. No gzip support — spec-mandated

OTLP spec: "All server components MUST support … `gzip` compression"
(otlp specification §transport compression). Exporters routinely gzip. The
handler reads a raw body, so gzip arrives as binary garbage → 400.
**[measured]** spec text confirmed at
`opentelemetry-proto/docs/specification.md` lines 92–95, 515–516.

### B3. Unbounded request body

`json.NewDecoder(r.Body)` with no `http.MaxBytesReader`. The OTLP spec
recommends a 64 MiB cap; prompt §15 explicitly names "compression bombs,
oversized attributes" as attacks to prevent. One malformed POST can OOM the
process. Fix: `MaxBytesReader` applied **before** decompression limits are
enforced by the decompressor (bounded `io.LimitReader` on the gzip reader).

### B4. Sort key makes the product's primary query the slowest one

`ORDER BY (service_name, http_route, outcome, start_time, trace_id)`. The
operation-detail page — the centrepiece of the product per prompt §13.2 —
looks up **one trace_id**, which is the 5th key column, so it cannot prune.
**[measured]** at 2M rows / 249 granules:

| Query | Granules read |
|---|---|
| `WHERE trace_id = …` (operation detail) | **249 / 249 — full scan** |
| `WHERE service_name = … AND start_time > …` (list) | 172 / 249 |

Fix (verified): add a projection ordered by `(trace_id, start_time)`.
**[measured]** `EXPLAIN indexes=1` on a table with that projection returns
`ReadFromPreparedSource (by_trace)` — the planner uses it. Keep the main sort
key for search, add the projection for retrieval.

### B5. Duplicate spans are stored twice

OTLP retries and at-least-once delivery are normal. Same `(trace_id, span_id)`
inserted twice → 2 rows. **[measured]** plain `MergeTree`: 2 rows;
`ReplacingMergeTree`: plain `count()` = 2 **until merged**, `FINAL` = 1.

That matters: "eventually deduped" means search results double-count until a
merge happens. Decision needed (see D2). `insert_deduplication_token` alone
does **not** fix it on plain `MergeTree` — **[measured]** 2 rows, because
non-replicated dedup is off by default; it works once the table sets
`non_replicated_deduplication_window=1000` (**[measured]** then 1 row). That
is per-batch idempotency, not per-span uniqueness — both are needed.

### B6. Documents state things that are false

False claims in the scaffold are worse than no docs, because they get believed.

| Where | Claim | Reality |
|---|---|---|
| `PLAN.md` | "Phase 1 ✅" | Phase 1 requires a host agent discovering a Go/Gin service **plus** ClickHouse persistence. Neither exists. ~half of Phase 1 is done, and the half that is the hard part (automatic instrumentation) is not started. |
| `docs/adr/0003`, `docs/risk.md` #6, `internal/otlpjson/types.go` | "hex IDs are a deviation; base64 conformance deferred" | Backwards. OTLP JSON uses **hex for `traceId`/`spanId` in all encodings**; base64 applies to other bytes fields. **[measured]** spec lines 454–457. The code is correct and the caveat invents a task that must never be done. |
| `README.md` | "Phase 0 complete" | Phase 0 also requires the target kernel/eBPF capability assessment and dependency licence/maintenance verification. Neither was done (risk #2 still open). |

## Must fix before the ClickHouse store (model/schema coupling)

These are cheap now and force migrations later.

### M1. `model.Span` is far too thin for the prompt's data model

Prompt §5.4/§6 require operation identity to include `rpc.*`,
`db.system`/`db.operation.name`/`db.query.summary`, queue system/name/job type,
span links, status message, host/pod/namespace/container, resource attributes,
`status` message, instrumentation completeness, and correlation confidence.
`model.Span` has HTTP + `error.type` only. If the DDL is written against it,
the first Postgres or Redis span forces `ALTER TABLE` plus a backfill. Expand
the struct first, DDL second.

### M2. Errors are only visible if the ROOT span failed

`outcome` comes from the root span's HTTP status. A trace whose root returns
200 while a child `db.query` timed out is reported `success`. This is exactly
the class of blind spot the platform exists to remove (the fare-membership
"order exists, history empty" shape). Need per-span outcome (present) **plus** a
trace-level rollup derived from all spans.

### M3. No redaction hook at all

Prompt §15 and §8.1 require redaction of `Authorization`, cookies, tokens,
credentials, and PII **before** the data leaves ingest. There is no interface,
no rule set, not even a stub. Once ClickHouse stores request attributes, every
missing rule becomes a data-retention incident. Define the interface now:
`ingest` must call a `Redactor` between decode and `InsertSpans`, even if the
first implementation is a small default set.

### M4. `attrsToMap` silently drops most attributes — chum

It handles `stringValue` and `intValue` only; `boolValue`, `doubleValue`,
arrays and kvlists are dropped without a counter. Code that *looks* like it
collects attributes while discarding them is worse than not collecting. Fix:
map all scalar kinds, count the dropped ones, expose the counter.

### M5. No attribute storage and no resource attributes

The schema has no `attributes` map and no resource columns beyond
service name/version/environment. So "which pod", "which SQL fingerprint",
"which HTTP client" are all unanswerable. Prompt §12 wants a *controlled*
secondary structure for high-cardinality attributes — design it
(`attributes` `Map(String,String)` with a bounded key allow-list, or a
separate attributes table) rather than adding columns ad hoc.

### M6. `NOT NULL` in the DDL is silently discarded

**[measured]** `SHOW CREATE TABLE` returns no `NOT NULL` — ClickHouse columns
are non-nullable by default and drops the clause. It reads as an enforcement
guarantee that does not exist. Remove it, and use `Nullable(...)` only where a
value is genuinely absent, deliberately.

### M7. Retention is hardcoded to one 14-day rule

`TTL toDateTime(start_time) + toIntervalDay(14)`. Prompt §10 requires
per-rule, per-method, per-route retention. **[measured]** ClickHouse supports
conditional TTL and this exact shape was **accepted**:

```sql
TTL ts + INTERVAL 2 DAY  DELETE WHERE http_method = 'GET' AND outcome = 'success',
    ts + INTERVAL 30 DAY DELETE WHERE outcome = 'server_error'
```

So per-rule retention can be enforced by the storage engine; no custom reaper
needed. That removes a whole component from the plan — record it as an ADR.

### M8. `store.Query` has no time range

Time is the primary search axis for every observability tool, and the query
struct cannot express it. Add `From`, `To`, and cursor pagination (`Limit` is
hardcoded to 100 with no paging).

### M9. The `Store` interface will not survive the policy engine

Prompt §10.2 requires the selected policy ID/version, sampling decision, and
redaction state to be persisted **with the record**. `InsertSpans([]Span)`
has nowhere to put that, so Phase 4 would break every implementation. Change
the signature now: `Insert(ctx, []Record)` where `Record{Span, Decision}`.

## Test gaps

Current tests: JSON→span mapping happy path; ingest→list→detail happy path;
404 for unknown trace. They are not vacuous (they fail if the pages render
empty), but they leave these untested: gzip, protobuf, oversized body,
malformed JSON, duplicate span, outcome matrix (2xx / 4xx / 5xx / OTLP status
ERROR / no status), dynamic-route normalization, and any ClickHouse path.
Prompt §19 requires all of the retention/sampling/TTL-vs-search assertions;
none exist yet. No benchmark exists for §17's budgets.

## Decisions this review forces (write these as ADRs)

- **D1 — retrievability vs searchability.** Main table `ORDER BY
  (service_name, http_route, start_time)` for search; projection
  `(trace_id, start_time)` for retrieval. Both measured. No second table.
- **D2 — duplicate strategy.** `ReplacingMergeTree` (dedupe at merge) **plus**
  `insert_deduplication_token` with `non_replicated_deduplication_window`
  (retry idempotency). Accept that plain `count()` can over-count between
  merges: list queries dedupe with `FINAL` only on the narrow
  single-trace path, never on aggregate scans.
- **D3 — retention in the engine, not in code.** Conditional `TTL … DELETE
  WHERE` per rule; the policy engine writes DDL/rule changes, and does not
  run a reaper loop.
- **D4 — model before schema.** The span record is expanded (M1/M2/M9) before
  `001_spans.sql` is rewritten, so the first migration is the only migration
  in Phase 1.
- **D5 — transport conformance is not optional.** protobuf + gzip + body limits
  land with the store work, because a store that cannot be fed by a real
  exporter is theatre.

## Implementation plan for (a) ClickHouse store — ordered to avoid rework

Each step leaves `go build ./...` and `go test ./...` green.

**S1. Repo hygiene** (30 min) — `git init`, `.gitignore`, `LICENSE`,
`docker-compose.yml` with ClickHouse pinned, `Makefile` (`dev-db`, `test`,
`migrate`), CI running build+vet+test. Move `pilot-projects.md` to `docs/`.

**S2. Model + contract** (1 h) — expand `model.Span` (rpc/db/queue/attributes/
status message/links/host+pod/confidence), add `model.Decision` (policy id +
version, sampled, redaction state), add trace-level outcome rollup, change
`Store.InsertSpans` → `Insert(ctx, []Record)`, add `Query.From/To/Cursor`.
Update the ADRs that are false (B6).

**S3. Ingest conformance** (2 h) — `http.MaxBytesReader`; gzip decode with a
bounded reader; protobuf via `go.opentelemetry.io/proto/otlp`; redactor
interface between decode and insert; malformed-span counter; tests for each.

**S4. DDL v2** (2 h) — replace `001_spans.sql`:
`ReplacingMergeTree(ingested_at)` + `PARTITION BY toYYYYMMDD(start_time)` +
`ORDER BY (service_name, http_route, start_time)` + projection
`by_trace (trace_id, start_time)` + conditional TTL (per-method/route/outcome)
+ `non_replicated_deduplication_window=1000` + `installed_at` column so
duplicates resolve last-write-wins. Add `schema_migrations` table. Verify by
re-running the granule measurements from this review in a test.

**S5. `store.ClickHouse`** (3 h) — implement the interface against `ClickHouse
26.10` via HTTP (`clickhouse-go/v2`), with:
insert batching (bounded), `FINAL` only on `GetTrace`,
`GROUP BY`-based dedupe for the list path, TTL/policy columns written at
insert. Integration tests gated by `LEUTIK_CLICKHOUSE_URL` (skip when absent)
so `go test ./...` stays green without Docker.

**S6. Verify against the review's own numbers** — re-run the two `EXPLAIN
indexes=1` measurements and the duplicate-insert measurement as assertions in
the integration test. The review's numbers become the regression bar.

**S7. Only then** the agent (Phase 1c), on Jupler.

Deliberately **not** in this plan: sampling engine, log ring buffers,
profiling, K8s, auth. They stay in their phases.
